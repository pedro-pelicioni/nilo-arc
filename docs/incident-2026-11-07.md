# Render health checks, 7 Nov 2026

Read-only evidence from the Render service `srv-dbjrdmqjnfac738rghdg`. Times are America/Cuiaba (UTC−4). This is not a claim that production is fixed. The live deploy is still commit `c989a6d4473ec67b1fe4542c48693b9d22ff1af6` on `main`. This branch is not that commit. `autoDeploy` is yes and the trigger is a commit, so merging to `main` deploys without a separate step.

## Proven

- The HTTP health check path is `/api/agent/status/0x0000000000000000000000000000000000000001`. It is not `/health`.
- Render treats that GET as the probe: 2xx or 3xx within 5 seconds passes. A timeout or a 502 fails it. Instances `6sfnq` (08:05:16) and `29nhl` (08:29:17) failed with HTTP 502. `bhj2f` and `tv448` failed with the 5 second timeout. `evicted` was false. Those records do not say out of memory, and they do not record SIGTERM or SIGKILL.
- At 07:49:55.818 the same `bhj2f` process logged `agent route failed: ContractFunctionExecutionError: Request exceeds defined limit.` Status 429, URL `https://rpc.mainnet.arc.io/`, details `rate limit exceeded`. The call was `eth_call` `mandateOf(address)` on `0x6debfa160cc1fd5ef06251690375d3887137e66c` for `0x0000000000000000000000000000000000000001`. The stack is `readContract` → `mandateOf` → `Promise.all` index 0 → the status handler, and viem's `withRetry` / `attemptRetry`. That is the public RPC quota, not an empty mandate and not a contract revert (`BadMandate`, `OverLimit`, and the rest).
- Another 429 was in the logs at 07:48:31. The 07:49:16 timeout on `bhj2f` is about 40 seconds before the 07:49:55 line. The 429 explains how this probe can fail. It does not prove that this exact call caused that timeout.
- Sampled CPU stayed near 0.03 of a 0.15 CPU limit. Sampled RAM stayed near 70–80 MiB of about 512 MiB (`bhj2f` peak 81,432,580 bytes, `tv448` peak 75,702,270 bytes). The samples are 30 seconds apart, have gaps, and CPU is not labeled per instance. They do not show saturation. They also do not rule out a short memory spike. Exit 137 on `tv448` (00:24:50 and 00:28:51) and `6sfnq` (08:14:37) is still unexplained.

## Not proven

- That walking NiloAgent history caused the 429.
- That the event loop was blocked.
- That the missing SIGTERM handler caused 137.
- That the process ran out of memory.

## What has to happen before calling this handled

Pedro approves both of these. Neither is done by the code alone.

1. Merging to `main` deploys this service. Do not merge until that deploy is wanted.
2. Changing Render's health check path to `/health` is a dashboard change. Do not change it until that is wanted. Until then the process has to keep answering the status URL above with a fast 2xx and no RPC, which this branch does.
